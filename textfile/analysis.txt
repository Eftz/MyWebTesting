# 🔍 Gap Analysis & Web Codebase Review: SmartLife Project

เอกสารนี้รวบรวมการวิเคราะห์ช่องว่างการพัฒนา (Gap Analysis) ระหว่าง spec กับ UI ดั้งเดิม รวมถึงผลการตรวจสอบโค้ดเพื่อปรับปรุงโครงสร้างของเว็บแอปพลิเคชันในโฟลเดอร์ `Myweb`

## 📁 ส่วนที่ 1: Gap Analysis (UI Mockup vs Concept Spec)

สรุปช่องว่างที่วิเคราะห์จากความต้องการแรกเริ่มเปรียบเทียบกับหน้าตาอินเตอร์เฟสเดิม

### สรุปสิ่งที่เห็นใน UI Mockup (6 หน้า)

| หน้า | เนื้อหา |
|:---|:---|
| Page 1 | **Sign In** — Username + Password, ปุ่ม Sign up / Sign in |
| Page 2 | **Sign Up** — Username + Password + Confirm Password, ปุ่ม Sign up, ลิงก์ Back to sign in |
| Page 3 | **Dashboard** — Sidebar (Dash!!! board~~, Transaction_$$, Do the < list >, Healthy Basement) + การ์ด 3 ใบบน main area |
| Page 4 | **Transaction_$$** — ฟอร์มเพิ่มรายการ (ชื่อ, จำนวนเงิน, ประเภท รายรับ/รายจ่าย) + ตารางรายการทั้งหมด (แก้ไข/ลบ) + Search |
| Page 5 | **Do the < list >** — ตาราง (time, topic, alert time, status) + Search + ปุ่ม edit&delete |
| Page 6 | **Healthy Basement** — การ์ด 3 ใบ: water 💧, exercise 🏋️, Eating Calory 🔥 |

### 🔴 สิ่งที่อยู่ใน Concept แต่ยังไม่เห็นใน UI Mockup

#### 1. Startup Activation Screen / Onboarding
- **รายละเอียด:** Concept ระบุว่า "เสร็จสิ้น" แล้ว แต่ใน UI mockup ไม่มีหน้า Onboarding ที่ให้ผู้ใช้ระบุ **ชื่อ, เป้าหมายการออม, ปริมาณน้ำดื่มเป้าหมาย, เวลาออกกำลังกายเป้าหมาย** ตอน first-time use
- **ควรเพิ่ม:** หน้า Onboarding wizard หลัง Sign Up ครั้งแรก ให้ตั้ง goals ส่วนตัว

#### 2. Doughnut Chart สัดส่วนรายจ่ายตามหมวดหมู่
- **รายละเอียด:** Concept ระบุว่ามี **Doughnut Chart (Chart.js)** แสดงสัดส่วนรายจ่ายแบ่งตามหมวดหมู่ แต่ใน UI ของ Transaction ไม่มีกราฟวงกลมอยู่เลย
- **ควรเพิ่ม:** แสดง Doughnut Chart ในหน้า Transaction หรือ Dashboard

#### 3. แถบเปรียบเทียบยอดคงเหลือ vs เป้าหมายออม
- **รายละเอียด:** Concept ระบุ "แถบเปรียบเทียบระหว่างยอดคงเหลือจริงและเป้าหมายการออมประจำเดือน"
- **ควรเพิ่ม:** Progress bar หรือ gauge แสดงเป้าหมายการออมใน Dashboard หรือ Transaction

#### 4. Progress Bar สุขภาพ (น้ำ/ออกกำลังกาย) + ปุ่มกดเพิ่มแบบ Real-time
- **รายละเอียด:** Concept ระบุ "แถบ Progress Bar แสดงอัตราเปรียบเทียบ" + "ปุ่มคีย์ลัดกดเพิ่มหน่วยบันทึกแบบ Real-time"
- **ควรเพิ่ม:** UI ภายในการ์ดแต่ละใบ (progress bar, ปุ่ม +, ค่าเป้าหมาย)

#### 5. ระบบล้างข้อมูลสุขภาพรายวัน (Daily Reset)
- **รายละเอียด:** Concept ระบุ "ระบบล้างข้อมูลเริ่มต้นใหม่เมื่อข้ามเข้าสู่วันถัดไป"
- **ควรเพิ่ม:** ระบุ logic ในเอกสาร concept ว่า reset ทำงานอย่างไรเมื่อมี authentication system

---

### 🟡 สิ่งที่อยู่ใน UI แต่ยังไม่ได้ระบุใน Concept

#### 1. ระบบ Authentication (Sign In / Sign Up)
- **รายละเอียด:** UI mockup มีหน้า Sign In / Sign Up แต่ concept ไม่ได้พูดถึงเลย
- **ควรเพิ่มใน concept:** ระบบ Authentication — เทคโนโลยีที่ใช้, การจัดเก็บ session, ขั้นตอน password recovery

#### 2. Eating Calory 🔥 (การนับแคลอรี่)
- **รายละเอียด:** UI ของ Healthy Basement มีการ์ด **Eating Calory** ซึ่ง concept ไม่ได้พูดถึง
- **ควรเพิ่มใน concept:** ฟีเจอร์ Calory Tracking — เป้าหมายรายวัน, วิธีบันทึก (manual หรือ เลือกจากรายการอาหาร), หน่วยที่ใช้

#### 3. ระบบ Search ในหน้า Transaction และ Do the list
- **รายละเอียด:** UI มี search bar แต่ concept ไม่ได้ระบุว่าต้องมีฟีเจอร์ค้นหา
- **ควรเพิ่มใน concept:** ค้นหารายการได้ตามชื่อ/ประเภท/ช่วงเวลา

#### 4. ปุ่ม edit & delete ของ Code View ใน Do the list
- **รายละเอียด:** UI มีปุ่ม edit&delete ที่ดูเป็น toggle mode
- **ควรเพิ่มใน concept:** ระบุ UX flow ของการแก้ไข/ลบ to-do items

#### 5. ไอคอน Settings (⚙) ข้าง Username ใน Sidebar
- **รายละเอียด:** ควรเพิ่มใน concept: หน้า Settings สำหรับตั้งค่า (เปลี่ยนชื่อ, เปลี่ยน password, ตั้ง/แก้ไขเป้าหมาย, theme)

## 💬 ส่วนที่ 2: บทวิเคราะห์และข้อคิดเห็นต่อข้อเสนอแนะทั้ง 8 ข้อของคุณ

จากการที่ผมได้เข้ามาตรวจสอบโค้ดและโครงสร้างของ SmartLife SPA Engine ที่พัฒนาไว้ในโฟลเดอร์ `Myweb` ผมเห็นด้วยกับคุณในทุกๆ ข้อเสนอแนะอย่างยิ่งครับ โดยมีบทวิเคราะห์และการลงลึกทางเทคนิคเพิ่มเติมดังนี้:

### 1. แยกไฟล์แต่ละหน้าให้ชัดเจน แล้วทำ Route Function ไปในแต่ละหน้า
- **เห็นด้วยอย่างยิ่ง (Highly Agree):** ปัจจุบันไฟล์ `app.js` มีขนาดใหญ่มาก (ประมาณ 90KB, 1,800+ บรรทัด) โครงสร้างโค้ดทั้งหมด (การจัดการ State, Web Audio, Notifications, หน้า UI ทั้ง 6 หน้า) รวมกันอยู่ในจุดเดียว ทำให้การดูแลและแก้โค้ดในอนาคตทำได้ยาก
- **แนวทางแก้ไข:** เราควรใช้วิธี **ES Modules (Native import/export)** ของบราวเซอร์ โดยไม่ต้องผ่านระบบ Build Tools (อย่าง Webpack หรือ Vite) เพื่อคงความเบาและรวดเร็วของโปรเจกต์เดิม โดยจะแยกเป็นโมดูลย่อยๆ เช่น `state.js`, `audio.js`, `notification.js`, `router.js` และหน้า UI Components แยกโฟลเดอร์อย่างชัดเจน

### 2. ในหน้า Transaction ให้เอาส่วนสรุปผลไปไว้เฉพาะหน้า Dashboard เท่านั้น
- **เห็นด้วยอย่างยิ่ง (Highly Agree):** เป็นแนวคิดการแยกหน้าที่ของคอมโพเนนต์ (Separation of Concerns) ที่ถูกต้องมากครับ หน้า Transaction ในเชิง UX ควรโฟกัสเฉพาะฐานข้อมูล/รายการล็อกธุรกรรม (Database logs) และฟอร์มสำหรับสร้าง/แก้ไขรายการใหม่ (CRUD Input Form) 
- **แนวทางแก้ไข:** ย้ายส่วนยอดรวมความคืบหน้าการออมเงิน (Savings Goal Progress) และกราฟสัดส่วนรายจ่าย (Doughnut Chart) ไปแสดงและคำนวณที่หน้า **Dashboard** ส่วนหน้า Transaction จะเหลือเพียงแค่ฟอร์มกรอกรายการและตารางประวัติธุรกรรมพร้อมระบบค้นหาที่โล่งและสะอาดตา

### 3. ควรทำการใส่ระบุเวลาให้ใช้งาน UI กดง่าย ๆ ทั้งใน Transaction และ Do the list ให้ User ไม่ต้องพิมพ์ยาก ๆ
- **เห็นด้วยอย่างยิ่ง (Highly Agree):** การพิมพ์วันที่หรือกรอกข้อมูลเวลากดผ่านช่องป้อนข้อมูลมาตรฐานเบราวเซอร์อาจจะพิมพ์ยากและช้า
- **แนวทางแก้ไข:**
  - **สำหรับ Date Input (Transaction / Todo):** เพิ่มปุ่มด่วนลัดข้างช่องกรอก เช่น `วันนี้`, `เมื่อวาน` (สำหรับย้อนบันทึกธุรกรรมได้ง่าย), `พรุ่งนี้` (สำหรับตั้ง Todo ล่วงหน้า) เพียงแค่คลิกเดียวจะดึงวันที่ปัจจุบันมาใส่ให้ทันที
  - **สำหรับ Time Input (Do the list - เวลาเตือนความจำ):** เพิ่มปุ่มเวลาลัดด่วน เช่น `ตอนนี้`, `อีก 15 นาที`, `อีก 30 นาที`, `อีก 1 ชม.` หรือปุ่มช่วงยอดนิยมอย่าง `18:00` เพื่อให้ผู้ใช้สามารถกำหนดระบบเสียงเตือนภารกิจด่วนได้ทันทีโดยไม่ต้องพิมพ์

### 4. Default หน้าแรกควรเป็น Sign In ไม่ใช่ Sign Up
- **เห็นด้วยอย่างยิ่ง (Highly Agree):** ผู้ใช้ส่วนใหญ่สมัครสมาชิกเพียงครั้งเดียว และต้องการเข้ามาใช้งานอย่างรวดเร็ว หน้าแรกที่ผู้ใช้ยังไม่ได้ล็อกอินจึงควรเข้าหน้าล็อกอิน (Sign In) เป็นค่าเริ่มต้น และใส่ปุ่มลิงก์สลับสำหรับผู้ใช้ที่ต้องการสมัครสมาชิก (Sign Up)

### 5. ประเภทธุรกรรม ควรเพิ่ม "เงินออม" แยกจาก รายรับ/รายจ่าย
- **เห็นด้วยอย่างยิ่ง (Highly Agree):** นี่เป็นระบบการจัดการเงินส่วนบุคคลที่ดีมาก เพราะ "เงินออม" ไม่ใช่แค่ตัวเลขเปรียบเทียบธรรมดา แต่เป็นธุรกรรมที่เกิดการย้ายกระเป๋าเงิน (หักจากรายรับไปออมทันที)
- **สูตรการคำนวณใหม่ที่จะปรับปรุง:**
  - **ยอดเงินที่สามารถใช้สอยได้จริง (Available Balance):** `รายรับ (Income) - รายจ่าย (Expense) - เงินออม (Savings)`
  - **ยอดเงินออมสะสมทั้งหมด (Total Savings):** ผลรวมของรายการทั้งหมดที่มีประเภทเป็น `เงินออม (Savings)`
  - วิธีนี้จะทำให้ผู้ใช้สามารถตั้งหัวข้อธุรกรรมเชิงรุกได้ เช่น "แบ่งเงินออมเข้าพอร์ตลงทุน 3,000 บาท" แล้วระบบจะหักเงินก้อนนี้ออกจากเงินใช้สอยทั่วไปทันที แต่จะแสดงค่าความคืบหน้ากระปุกออมเงินเพิ่มขึ้น!

### 6. ปุ่มการจัดการควรเพิ่มฟังก์ชัน Edit ให้เลือกได้นอกเหนือจาก Delete
- **เห็นด้วยอย่างยิ่ง (Highly Agree):** ปัจจุบัน UI ซ่อนปุ่มแก้ไข (Edit) และลบ (Delete) ของแถวรายการต่างๆ ไว้ข้างใต้ปุ่ม toggle "จัดการรายการ (Shopee Bucket)" ซึ่งทำให้ค้นหาได้ยาก
- **แนวทางแก้ไข:**
  - ปรับปรุงให้แถวรายการประวัติธุรกรรมและภารกิจแสดงปุ่ม **แก้ไข (Edit)** และ **ลบ (Delete)** แบบเข้าถึงได้รวดเร็วขึ้นในโหมดปกติ (เช่น แสดงเมื่อผู้ใช้นำเมาส์ไปชี้ hover หรือวางเป็นไอคอนสวยงามให้กดง่ายๆ)
  - ในส่วนของปุ่มจัดการแบบกลุ่ม (Shopee Bulk Action) นอกจากการลบหลายรายการพร้อมกันแล้ว ในหน้า Do the list จะเพิ่มความสามารถในการเปลี่ยนสถานะ เช่น "ทำเครื่องหมายว่าทำเสร็จแล้วทั้งหมด (Mark Completed)" ด้วย

### 7. การแจ้งเตือนสำเร็จ ควรเป็นติ๊กในช่องของแถบแจ้งเตือนเวลา ไม่ควรทำแยกสีเขียวจะทำให้สับสน
- **เห็นด้วยอย่างยิ่ง (Highly Agree):** ปัจจุบัน UI ของภารกิจมีการ์ดภารกิจที่แสดงแถบ "เตือนเวลา XX น." แยกชิ้นกับ Badge สีเขียว "เตือนสำเร็จ" หรือ Badge สีเหลือง "กำลังรอเตือน" ทำให้ข้อมูลแสดงผลซ้ำซ้อนและดูรกสายตา
- **แนวทางแก้ไข:** ยุบส่วนบอกเวลาและส่วนบอกสถานะแจ้งเตือนเข้าไว้ด้วยกันใน Badge เดียว เช่น:
  - **รอแจ้งเตือน:** แสดงไอคอนนาฬิกา พื้นหลังสีเหลือง/ส้ม ⏰ `เตือนเวลา 18:00 น. (รอเตือน)`
  - **เตือนสำเร็จแล้ว:** แสดงไอคอนติ๊กถูก พื้นหลังสีเขียว ✅ `เตือนเวลา 18:00 น. (เตือนสำเร็จ)`
  - ซึ่งจะช่วยให้ผู้ใช้รับรู้ข้อมูลได้จบในชิ้นเดียวอย่างสวยงามและเข้าใจง่ายที่สุด

### 8. ปุ่มรีเซ็ตค่าวันใหม่ใน Healthy Basement ไม่ควรลบ Icon ใน Navbar
- **เห็นด้วยเป็นอย่างยิ่ง (Highly Agree):** ข้อนี้เป็นประเด็นที่วิเคราะห์และเฉียบคมมากครับ!
- **สาเหตุเชิงเทคนิคที่ผมตรวจสอบพบ (Technical Bug Discovered):** 
  ในไฟล์ `app.js` ฟังก์ชันอัปเดตข้อมูลสุขภาพและปุ่มรีเซ็ตประจำวัน เช่น `resetWater()`, `resetExercise()`, `addWater()` ฯลฯ เมื่อคำนวณเสร็จจะมีการเรียกคำสั่งบันทึกข้อมูลและรัน `renderPage()` เพื่อโหลดวาดภาพ Layout หน้าจอใหม่ทั้งหมด
  **ปัญหาคือ:** ในขั้นตอนสุดท้ายของฟังก์ชัน `renderPage()` *ไม่ได้ระบุคำสั่งประมวลผลวาดไอคอน SVG ใหม่* (`lucide.createIcons()`) เหมือนตอนที่เราสลับหน้าผ่านฟังก์ชัน `navigate()` ดังนั้น ทันทีที่ผู้ใช้คลิกปุ่มรีเซ็ตหรือปุ่มเพิ่มในหน้า Healthy Basement หน้าจอจะถูกวาดใหม่ ส่งผลให้ไอคอนทั้งหมดบนแถบนำทาง (Navbar) และไอคอนอื่นๆ ของเพจหายไปจนหมด!
- **แนวทางแก้ไข:** เพิ่มคำสั่ง `if (window.lucide) lucide.createIcons();` ลงไปท้ายฟังก์ชันวาดผลหลัก `renderPage()` เสมอ เพื่อรับประกันว่าไอคอน SVG ทุกตัวจะคงอยู่สวยงามและไม่หายไปเมื่อหน้าจอวาดใหม่

## 🛠️ ส่วนที่ 3: สิ่งที่ตรวจสอบพบและต้องการแนะนำเพิ่มเติมเพื่อความสมบูรณ์แบบ

จากการตรวจสอบโครงสร้างและโค้ดภายใน `Myweb` อย่างละเอียด ผมพบสิ่งที่ควรปรับปรุงเพิ่มเติมดังต่อไปนี้ เพื่อยกระดับให้เว็บ SmartLife ของคุณมีความเป็น Premium และ State-of-the-Art มากยิ่งขึ้น:

### 1. การปรับปรุงระบบ Form Validation
- **ปัญหาปัจจุบัน:** ปัจจุบันไม่มีกลไกเช็คข้อผิดพลาดในการกรอกข้อมูลฟอร์มมากนัก เช่น ในหน้า Transaction สามารถพิมพ์ยอดเงินติดลบได้ ซึ่งอาจทำให้การรวมบัญชีผิดพลาด หรือหน้าสมัครสมาชิกที่สามารถตั้ง Username แบบเว้นวรรคได้
- **ข้อแนะนำเพิ่มเติม:** เพิ่มระบบ Validate ข้อมูลเบื้องต้นที่รัดกุมก่อนส่งฟอร์ม (เช่น ตรวจสอบยอดเงินต้องมากกว่าศูนย์, ป้องกันการพิมพ์ตัวอักษรแปลกๆ ในฟิลด์ตัวเลข) พร้อมแสดงดีไซน์การแจ้งข้อผิดพลาด (เช่น ขอบกล่องอินพุตเป็นสีแดงพร้อมข้อความช่วยเหลือสีแดงเตือนใต้กล่องอินพุต) เพื่อให้ผู้ใช้ทราบว่าตนกรอกข้อมูลผิดพลาดตรงไหน

### 2. การสร้าง Micro-animations เพื่อ WOW ผู้ใช้
- **ปัญหาปัจจุบัน:** การสลับหน้าไปมาค่อนข้างแข็งกระด้าง (Instant swap) ขาดความมีชีวิตชีวา
- **ข้อแนะนำเพิ่มเติม:** เพิ่ม Micro-animations โดยใช้ Vanilla CSS ใน `styles.css` เช่น การกำหนดทรานซิชันเฟดและเลื่อนขึ้นเบาๆ (Slide-up & Fade-in transition) ให้กับ main area เสมอเมื่อมีการเปลี่ยนหน้าเพจ เพื่อความสมูทลื่นไหลระดับพรีเมียม

### 3. การป้องกันข้อผิดพลาดกรณี LocalStorage ว่างเปล่า (Edge Case Protection)
- **ปัญหาปัจจุบัน:** หากผู้ใช้ล้างข้อมูลแคชของเบราว์เซอร์หรือเพิ่งเคยเปิดใช้งานเว็บเป็นครั้งแรก บางฟังก์ชันอาจเกิดข้อผิดพลาด Null Pointer ได้หากไม่มีตัวแปรเริ่มต้นในคีย์
- **ข้อแนะนำเพิ่มเติม:** ใส่ตัวแปร Default และโครงสร้างข้อมูลสแตนด์บายที่ปลอดภัยใน `state.js` เสมอ เพื่อป้องกันไม่ให้เว็บหยุดทำงานหากเกิดการเคลียร์ข้อมูล LocalStorage

## 📂 ส่วนที่ 4: แผนผังโครงสร้างการแยกโฟลเดอร์และไฟล์โมดูลาร์ใหม่

ในการแยกสถาปัตยกรรมของ `app.js` ขนาดใหญ่ ออกมาเป็นโมดูลย่อยที่มีระเบียบตามข้อเสนอแนะข้อที่ 1 เราจะทำการแบ่งโครงสร้างไฟล์ของโฟลเดอร์ `Myweb` ใหม่ออกเป็นดังนี้ (โดยจะสลับไปใช้ `<script type="module" src="app.js"></script>` ใน HTML):

```text
Myweb/
├── index.html              # SPA Main Frame & Shell HTML
├── styles.css              # CSS Design System & Global Styles
├── app.js                  # จุดเริ่มต้นระบบ (SPA Bootstrapper / Main Entry)
└── js/                     # โฟลเดอร์รวมสคริปต์ระบบโมดูลย่อย
    ├── state.js            # ระบบจัดการ State ทั้งหมดของแอพ รวมถึงการจัดเก็บใน LocalStorage และ alarm ตรวจสอบภารกิจ
    ├── audio.js            # ระบบจำลอง/เล่นเสียงเตือนสังเคราะห์ด้วย Web Audio API (Chime Player)
    ├── notification.js     # ระบบติดต่อสื่อสาร Web Notification API สำหรับส่งข้อความ Push เด้งเตือนภายนอก
    ├── router.js           # ระบบควบคุมเส้นทาง Router, Layout Sidebar และการวาดเพจ SPA
    └── components/         # โฟลเดอร์เก็บ Module ส่วนควบคุม UI ของแต่ละหน้าเว็บย่อย
        ├── auth.js         # จัดการหน้าล็อกอิน / สมัครสมาชิก (Default: Sign In)
        ├── onboarding.js   # จัดการหน้ากรอกเป้าหมายแรกเริ่ม (First-time Onboarding Wizard)
        ├── dashboard.js    # หน้าสรุปภาพรวมความคืบหน้า รวมถึงกราฟ Doughnut Chart และยอดออมเงินสะสม
        ├── transaction.js  # หน้าบันทึกบัญชี จัดการ รับ / จ่าย / ออม (บันทึก CRUD & Log ประวัติตาราง)
        ├── todo.js         # หน้าวางแผนภารกิจประจำวันและแจ้งเตือนเวลา (Do the list)
        ├── health.js       # หน้าดูแลสุขภาพ บันทึกน้ำ, ออกกำลังกาย และแคลอรี่ (Healthy Basement)
        └── settings.js     # หน้าตั้งค่าโปรไฟล์และเป้าหมายรายวันทั่วไป
```

---

*สรุปผลการวิเคราะห์และข้อแนะนำทั้งหมดนี้ได้ทำการรวบรวมเข้าไว้ในไฟล์ `analysis.txt` เรียบร้อยแล้วครับ*
*(หมายเหตุ: ได้ทำการปรับโครงสร้างไฟล์เว็บทั้งหมดในโฟลเดอร์ Myweb เรียบร้อยแล้ว)*

## 📝 ส่วนที่ 5: รายการที่ต้องแก้ไขเพิ่มเติม (Additional Fixes Requested)
จากการอัปเดตความต้องการของคุณ ได้ทำการโน้ตรายการที่ต้องปรับปรุงแก้ไขเพิ่มเติมดังนี้:

1. **การเรียงลำดับประวัติการเงินทั้งหมด (Transactions Sorting)**
   - **ความต้องการ:** รายการประวัติการเงินทั้งหมดจะต้องถูกจัดเรียงตามวันที่ใหม่สุดขึ้นก่อนเสมอ เมื่อมีการเพิ่มธุรกรรมใหม่หรือแก้ไขธุรกรรมเดิม
   - **แนวทางแก้ไข:** เพิ่มระบบ Sort ข้อมูลใน `state.js` ทั้งในขั้นตอนบันทึก `saveTransactions()` และขั้นตอนการโหลดข้อมูล `loadUserData()` เพื่อรับประกันว่าข้อมูลธุรกรรมในระบบจะเรียงลำดับตามเวลาล่าสุดเสร็จสรรพก่อนนำไปแสดงผล

2. **การลบปุ่มลบเดี่ยวในหน้า Do the list (Row Actions)**
   - **ความต้องการ:** เอาปุ่มลบ (Delete) เดี่ยวที่อยู่ข้างปุ่มแก้ไขออกในโหมดจัดการรายการ (Shopee Bucket) เนื่องจากระบบรองรับการกดติ๊กกล่องเพื่อลบทีละหลายๆ รายการพร้อมกันได้อยู่แล้ว เพื่อลดความซ้ำซ้อน
   - **แนวทางแก้ไข:** ตรวจสอบและเอาปุ่มลบในแถวรายการภารกิจออก โดยคงเหลือเฉพาะปุ่มแก้ไข (Edit) และควบคุมการลบผ่าน Checkbox และปุ่มลบรวมด้านบน

3. **การรีเฟรชค่าการแสดงผล Do the list ทันทีหลังบันทึก (State Syncing)**
   - **ความต้องการ:** บันทึกภารกิจใหม่หรือแก้ไขภารกิจเดิมแล้ว ให้ระบบทำการอัปเดตและแสดงผลข้อมูลที่แก้ไขล่าสุดบนหน้าเว็บทันที
   - **แนวทางแก้ไข:** เมื่อทำรายการบันทึก/แก้ไขเสร็จใน `handleTodoSubmit()` จะยกเลิกโหมด Edit/Selection ของรายการเดิม และเคลียร์คำค้นหาในช่องค้นหา (Search) เพื่อให้หน้าเว็บรีเฟรชดึงข้อมูลทั้งหมดมาอัปเดตปัจจุบันได้ทันทีอย่างชัดเจน

4. **การเปิด/ปิด Navbar (Collapsible Sidebar Navigation)**
   - **ความต้องการ:** หน้า Dashboard หรือ Shell หลัก ควรมีปุ่มควบคุมเพื่อเลื่อนพับเก็บหรือเปิดแถบนำทาง (Navbar) เพื่อความสวยงาม ดูทันสมัยและไม่รกตา
   - **แนวทางแก้ไข:** สร้างฟังก์ชัน `toggleSidebar()` ควบคุมตัวแปร `sidebarCollapsed` ในระบบ โดยหากพับเก็บ (Collapsed):
     - สำหรับหน้าจอคอมพิวเตอร์ (Desktop): แถบนำทางจะหดเล็กลงเหลือเพียงแถบไอคอน (w-20)
     - สำหรับหน้าจอโทรศัพท์ (Mobile): แถบนำทางจะซ่อนไปทั้งหมดเพื่อเปิดพื้นที่การแสดงผลสูงสุด
     - เพิ่มปุ่มไอคอนเมนูพับที่มุมซ้ายบนของ main view เพื่ออำนวยความสะดวกในการเปิดปิดได้ตลอดเวลา

5. **การใช้ปฏิทิน (Calendar Picker) สำหรับป้อนข้อมูลวันที่**
   - **ความต้องการ:** สำหรับฟิลด์ข้อมูลประเภทวันที่ ให้สามารถเลือกจากปฏิทินที่ดูดีแทนการพิมพ์วันที่ด้วยตัวเอง
   - **แนวทางแก้ไข:** ปรับปรุง input ของวันที่ในหน้า Transaction และหน้า Todo ให้ใช้ `<input type="date">` พร้อมผูกคำสั่ง `onclick="this.showPicker()"` และตั้งค่าเริ่มต้นของฟิลด์เป็นวันที่ปัจจุบัน (Today) ทันทีที่เปิดหน้าจอ ทำให้สะดวกรวดเร็วและมองเห็นปฏิทินได้อย่างชัดเจน
